## Fixed in this pass

### 1. Background-task X did nothing on a failed row

**Report:** a background task reading `Background command "Run builds and tests in
background" failed with exit code 144` could not be cleared with its X.

**Cause:** `background-tasks/track.tsx` wired every _active_ row's clear button to
`handleClearCompleted`, which ignores its argument and clears `completedIds`. A failed
row is `requiresAttention`, so `isBackgroundTaskRowTidyEligible` deliberately keeps it in
the **active** list — its id was therefore never in `completedIds` and the X was a no-op.
(The type system missed it because a `() => void` is assignable to `(ids) => void`.)

**Fix:** active rows pass `onClearCompleted` directly, so Clear targets that row's id.

### 2. Background-tasks header wording

**Report:** `"3 background tasks · 1 running"` is not useful; wanted the sub-agents shape.

**Fix:** `formatHeaderLabel` now takes the same partition the list renders and mirrors
`subagents/track-presentation.ts`: `"1 active background task · 2 completed background
tasks"`. It summarizes the two groups shown below it instead of inventing a third
framing, and it counts a pinned row in the group it is actually displayed in.

"active" not "running" on purpose — the active group also holds terminal-but-attention
rows (item 1), so "running" would be false.

### 3. Matrix effect density, alphabet, and vertical offset

**Report:** glyphs sit too far apart, density varies with label length, wanted
prose-like ASCII (≈80% lowercase / 20% uppercase, with symbols), and the strip reads
about 1px high.

**Cause of the density drift:** `MAX_RAIN_COLUMNS = 48`. `buildRainColumns` absorbs the
cap by _widening_ the pitch so the rain still reaches the end of the label — so any label
past ~380px got progressively sparser the longer it was. Short labels never hit the cap
and kept the tight 8px pitch. That is exactly the "short strings condensed, long strings
disparate" report.

**Fix:** cap raised to 128 (covers ~900px at the new pitch, so real single-line tool
labels never reach it and density is constant), `cellWidth` 8 → 7, `staggerSeconds`
0.045 → 0.027 so ~16 columns are lit at once instead of ~10. Alphabet rebuilt by
repetition (`pickGlyph` samples uniformly, so repetition _is_ the weighting): a–z ×4,
A–Z ×1, digits ×2, symbols ×1. Overlay gets `translateY(1)`.

### 4. Markdown syntax read aloud by TTS

**Report:** hashes are spoken when reading markdown replies; only the text rendered on
screen should be read.

**Fix:** new `packages/server/src/server/speech/speech-text.ts` —
`markdownToSpokenText()`, applied at `splitTextForTts` in `tts-manager.ts`. That is the
single choke point both TTS paths funnel through, so **voice mode and the per-message
playback button are both covered** by one pass. Strips headings/emphasis/bullets/
blockquotes/rules/table pipes, speaks link labels and image alt text rather than URLs,
keeps inline code, and unescapes backslash escapes.

**One deliberate departure from "read what is rendered":** fenced code blocks are
replaced with the spoken marker `"code block."` rather than read out. Reading a diff or
shell transcript aloud buries the prose. Flip `CODE_BLOCK_SPOKEN` handling if the
literal reading is wanted.

### 5. Playback could not be stopped once started

**Report:** "while playback is happening, we need a stop button… right now we cannot stop
once it's started."

**Cause:** the button already toggles to Stop on second press — but it lives in
`CompletedTurnFooterRow`, which honors the _hide chat message details_ appearance setting
by dropping to `opacity: 0` with `pointerEvents: "none"` unless hovered. The moment the
pointer left the row, the only Stop control was both invisible and unclickable.

**Fix:** new `agent-stream/message-playback-activity.ts`, a `useSyncExternalStore`
registry — state lives in the button, but the component that must react to it is an
ancestor. The button claims the registry on press and releases it on
stop/finish/error/unmount, and a speaking message keeps its button on screen regardless
of hover. Keyed by message rather than a global boolean, so one speaking message does not
reveal every button in the chat. Exactly one can speak at a time by construction
(starting playback flushes the queue and aborts in-flight synthesis), and a superseded
message's late unwind cannot clear the newcomer's claim.

This was originally scoped to the turn footer; item 12 moved the button onto the bubble
and the registry moved with it unchanged, now keyed by bubble group.

### 6. Active-line background hid the selection (CM6)

**Report:** "the active line gets a background colour that takes precedence over the
highlight color, so you can't see any text you have highlighted on the current line."

**Cause:** two facts that are only fatal together. `@codemirror/view`'s
`highlightActiveLine` decorates the caret's line **unconditionally** — including while
you are selecting — and `drawSelection` renders into `.cm-selectionLayer` at
`z-index: -1`, i.e. _behind_ the content. Our active-line fill is an opaque theme
surface on the `.cm-line` element, so it covered the selection completely. CM6's own
default (`#cceeff44`) is translucent, which is why upstream never hits this.

**Attempt 1 (rejected):** `highlightActiveLineUnlessSelecting` emitted no decoration while
any range was non-empty — with something selected there was no active-line tint at all.
Report: that trades one for the other; both should be visible at once.

**Attempt 2 (rejected):** `activeLineLayer`, a CM6 `layer({above: false})` registered
after `drawSelection()` so it stacks underneath, drawing a `RectangleMarker` per caret
line. Correct in principle. It shipped misaligned — marker coordinates are not document
coordinates (layers mount on `view.scrollDOM` and position against `getBase()`, so marker
`(0,0)` is left of the **gutters** and above `.cm-content`'s padding, while `BlockInfo.top`
is document-space) — and after that conversion was fixed the report was that the gutter,
the row and the selection were still three different heights: "we radically broke and
misaligned the gutter, the rows and the selection."

**Fix:** stock `highlightActiveLine()` — a plain `.cm-line` background — with
`activeLineBackground` made **translucent** (`withAlpha(foreground, 0.06)`, well under the
selection's 0.15/0.20 so an overlap still reads as selected). This is exactly what CM6
does with its own `#cceeff44` default. The two halves are one rule: translucent is what
lets a line decoration survive over the selection layer, and a line decoration is what
guarantees alignment — it _is_ the row's box rather than a rectangle computed to match
one. If the current line needs more presence, raise the alpha.

The meta-lesson, worth more than the fix: two of the three attempts failed on geometry
that no type or lint check can see, and this environment has no way to look at the result.
Prefer the construction that is correct _by definition_ over the one that is correct _by
calculation_.

### 7. Search highlight was invisible; caret was hard to find

**Cause (search):** `buildEditorThemeSpec` set `searchMatchBackground` to
`terminal.selectionBackground` — the _same value_ as the selection, at 0.15–0.2 alpha.
A match was therefore indistinguishable from selected text, which is precisely the
state you are in while stepping through results.

**Fix:** search matches are now amber (the semantic `statusWarning*` surfaces, already
calibrated per scheme) with an outline — `1px` on a match, `2px` plus the stronger fill
on the active one, so "which hit am I on" reads at a glance. `outline` rather than
`border` so an inline mark never reflows the line. New spec fields:
`searchMatchBorder`, `activeSearchMatchBorder`.

**Fix (caret):** new `cursorWidth` spec field, 2px, replacing CM6's 1.2px hairline.

### 8. Markdown soft breaks rendered as hard breaks

**Report:** "it's taking line breaks literally — I think normally line breaks in the
source are supposed to be ignored."

**Cause:** the `softbreak` render rule emitted `"\n"` (react-native-markdown-display's
own default, which we had inherited at both call sites). A *hard*break is an explicit
line break; a *soft*break is just a newline in the source, which markdown reflows as a
space. Every hard-wrapped paragraph therefore rendered as a ragged column.

**Fix:** `softbreak` emits `" "`; `hardbreak` still emits `"\n"`. Note this is the
**shared** renderer — it changes assistant messages as well as the file preview.

### 9. Markdown links rendered as plain text

**Cause:** react-native-markdown-display builds `inheritedStyles` from ancestor node
types, so the `text` inside a `link` _does_ receive the link style — but our `text` rule
then applies `styles.text`, which sets an explicit `color`, and in RN the innermost
explicit color wins. Colored wrapper, uncolored text.

The assistant-message renderer had always carried a private workaround for this
(cloning children to force the color); the _shared_ rule had none, which is why the file
preview was the surface where links looked like prose.

**Fix:** that workaround is now `withMarkdownLinkColor` in `markdown/renderer.tsx`, used
by both rules. Links stay color-only — **no** underline (explicitly rejected).

### 10. Reload-from-disk banner had no warning tint

**Fix:** both editor sync banners (disk-change and save-conflict — same class of "disk
and buffer disagree, you must choose") now use `statusWarningSurface` /
`statusWarningMuted`, with the alert glyph on `statusWarningStrong` instead of muted
grey. Worth knowing for the "formalize the tints" ask below: **the palette largely
already exists** — `statusWarning|Danger|Success|Info|Merged` each with a `Surface`
variant, plus `WarningMuted`/`WarningStrong`, all alpha fills so they tint the active
theme's surface rather than replacing it. The remaining work is documenting it in
`docs/design.md` and adopting it, not inventing it.

### 11. Find-in-file vs find-in-files shortcuts

**Finding:** the feared Ctrl-F clash does not exist — Ctrl-F is bound inside CodeMirror's
own keymap, so it only fires while an editor has focus and never shadows a global.

The real collision was elsewhere: **Ctrl+Shift+F was Toggle focus mode**, and project
search was on **Ctrl+S** (which is Save in the editor).

**Fix (user decision):** focus mode moved to **Mod+Alt+F** (matching theme cycling, which
already lives on Mod+Alt); **Mod+Shift+F** now opens the search sidebar — the combo every
other editor uses for find-in-files. The old Mod+S binding for search is left in place.
New help entry `find-in-files`, translated in all 7 locales.

### 12. One play button per turn instead of per message

**Report:** "Sometimes a turn produces multiple message blocks. I want a play button for
each one, NOT one at the end of the turn that plays back ALL of the messages."

**Cause:** the button lived in the turn footer, whose `getContent` is
`collectAssistantTurnContent` — it walks back to the preceding user message and joins
**every** assistant message in the turn. One press read the whole turn aloud.

**Granularity (user decision):** per _visual bubble_ — each contiguous run of text
between tool calls — not per markdown block. That distinction matters because a streamed
reply is promoted one markdown block at a time into separate `assistant_message` rows
sharing a `blockGroupId` (`types/stream.ts`), and those rows butt together into a single
bubble. Per-block would have put several buttons inside what reads as one message.

**Fix:** `AssistantBubblePlayback` in `message.tsx`, rendered on the segment that _ends_
a group (`spacing` `"default"` or `"compactTop"`), absolutely positioned at the bubble's
bottom-right with a circular chrome, hover-revealed (always visible on native/compact,
and always while speaking). New registry
`agent-stream/assistant-bubble-text.ts`: every segment reports its text under
(groupId, blockIndex) and the button reads them back joined in block order — a row cannot
see its siblings, so the group's full text has to come from somewhere. Segments report
the **store** text, never the typewriter-revealed slice, so playback is full fidelity
mid-reveal.

**Removed:** the turn-footer playback button, and `agent-stream/assistant-turn-width.ts`
with it — that registry existed solely to pin the footer button to the bubble's right
edge, and had no other consumer once the button moved onto the bubble.

### 13. Large pasted code blocks pushed the send button off screen

**Report:** pasting a few hundred lines into the composer grows it until the send button
is no longer reachable. Asked for a max height plus internal scroll.

**Cause:** the max height and the internal scroll both already existed — the cap was just
measured against the wrong box. `resolveMaxInputHeight` took `useWindowDimensions().height`
and returned `max(160, windowHeight * 0.5)`. The window is not what the composer has to
fit inside: a chat pane in a split is far shorter, and the `max(160, …)` floor meant a
genuinely short pane got a cap _taller_ than the pane. The cap also covered the text input
alone, ignoring the toolbar row and wrapper padding stacked below it, so the composer's
real height always exceeded its own cap. `inputAreaWrapper` doesn't shrink (`flexShrink`
defaults to 0 in Yoga) while its sibling transcript is `flex: 1`, so once the composer
outgrew the pane the transcript collapsed to zero and the overflow spilled out the bottom
— taking the toolbar, and the send button on it, with it.

**Fix:** `composer/input/max-height.ts` — a pure `resolveMaxInputHeight({viewportHeight,
isCompact})`. The ratio now bounds the **whole composer**, not just the input: the
non-input chrome (68px — wrapper padding, toolbar gap, border, toolbar row) is subtracted
from the share, which is what keeps the send button inside the measured box. 0.5 of the
viewport regular, 0.4 compact (the on-screen keyboard already covers most of a phone
pane). The `max(160, …)` floor is gone; 160 survives only as the pre-measurement fallback.

`viewportHeight` is measured by the host and threaded down as an optional prop
(`useContainerHeight`, quantized to 8px). Both chat surfaces report it — `agent-panel.tsx`
on its `root` view, `composer/draft/workspace-tab.tsx` on its `FileDropZone` (which gained
an `onLayout` passthrough). Both are boxes whose height their own parent owns, so a
growing composer can't feed back into the number capping it. Hosts that don't measure
(setup dialog, new-workspace screen) fall back to the window height, i.e. today's
behavior.

### Editor / markdown rendering

- ~~**Mermaid does not render** in markdown preview.~~ FIXED. Fences render in chat, the file
  viewer and the PR panel; `.mmd`/`.mermaid` files render as a single diagram. Web/Electron
  render in-page through a lazily imported mermaid; iOS/Android through a self-contained
  webview payload. Design notes now live in
  [docs/markdown-rendering.md](../../docs/markdown-rendering.md).
- **Auto-scroll fights you when editing at an off-screen caret** — FIXED. Reproduced in
  **plain editor mode, file opened normally**, which killed both standing hypotheses at
  once: the split-view scroll sync (`onScrolled`/`onPointerSelect` are `undefined` when
  `split` is false) and reveal-on-open (`revealTarget` returns early with no `lineStart`).
  Repro: caret on an early line, scroll it out of view, type — the editor does not follow
  the caret; scroll back to it and keep typing and the view snaps _away_ again.

  **Cause (CM6-internal):** CM6 tags text input with `scrollIntoView: true` and even
  extends its viewport to include an off-screen target (`@codemirror/view` 6.43.6,
  `ViewState.update` ~L6289), so a bare editor follows the caret on its own. In this
  embedded setup that pass intermittently doesn't land — when the caret's line is outside
  the rendered viewport at measure time the scroll target is consumed without scrolling,
  and the anchor-stabilization pass then re-pins the previous scroll offset (the "snaps
  back" symptom). Nothing in our own code sets `scrollTop` in plain mode, so this is CM6's
  own measure loop, not a feedback loop.

  **Fix:** `editor-core.ts` re-asserts the caret after a _user_ edit, on the next frame,
  skipped for `setDoc` (revert / disk reload / conflict reload) so a programmatic
  replacement doesn't yank scroll. **Note:** the reveal originally re-dispatched
  `EditorView.scrollIntoView(head)`, but the search item below proved CM6's own scroll lands
  the scroller ~175px off, so the reveal was reworked to scroll to the head's real rendered
  position (`coordsAtPos`) — see `revealSelectionInView` and the search item. Shared core,
  native webview bundle rebuilt (`build:editor-webview`).

- **Stepping through Search matches left the match ~10 lines above the viewport** (out of
  view) — FIXED, and the fix is now the general reveal mechanism for the whole editor.

  Two wrong turns first, both instructive. (1) Guessed the split-view scroll sync — dead,
  reproduced in plain mode. (2) Guessed `scrollRectIntoView` walking to a scrollable
  ancestor (`@codemirror/view/dist/index.js` ~L540 does walk up and scroll every scrollable
  ancestor, stopping only at `position: sticky|fixed`) and made the CM6 host `<div>` in
  `code-editor.tsx` (`HOST_STYLE`) `position: sticky` to stop the walk. **A console probe
  in the running app settled it:** `MATCH offset from scroller top: -175` (≈10 lines) with
  `scrollable ancestors: NONE`. So there is no ancestor — CM6 lands its **own** `.cm-scroller`
  at the wrong offset (its height-map estimate for the jump) and never self-corrects. The
  sticky change was then **reverted**: the probe proved no scrollable ancestor exists at all
  (that check is independent of the sticky), so it was dead weight — and `position: sticky`
  on the contenteditable host made the browser's scroll-selection-into-view jump downward on
  every text selection (a fresh bug). Net: the ancestor-walk theory was wrong, and the only
  change that mattered is the coords-based reveal below.

  **Fix (`editor-core.ts`):** stop trusting CM6's height-map math for the reveal. A new
  `revealSelectionInView(view)` reads the selection head's **actual rendered rectangle**
  (`coordsAtPos`, ground truth once the line is rendered — which it is, since CM6 lands
  close enough to render the region) and nudges `.cm-scroller` directly so the target sits a
  comfortable margin inside the viewport (no-op when already within that band). It is
  scheduled one frame after CM6's own pass (so it corrects the mis-landing) from: user
  edits (the off-screen-caret fix, now coords-based instead of a re-dispatched
  `scrollIntoView`), `findNext`/`findPrevious`/`replaceNext`, and `goToLine`/`selectLines`.
  Falls back to the height map only if the line is somehow unrendered (very far jump).
  Shared core → native webview bundle rebuilt (`build:editor-webview`). Split-view note: the
  correction uses `setScrollTopSuppressed`, so a search step won't drive the preview in
  split mode — acceptable, revisit if reported.

### Visualizer

- **Actions disappear while still running.** Perception is a timeout: a long bash/read/write
  shows, hides, then reappears when it completes and disappears again. Not noticeable on
  short actions. Suspect a fixed TTL on the action node rather than a lifecycle tied to the
  tool call's own start/end.
- **Discoveries need to fade away** (opposite of actions, which should persist while
  running) and **their colors read as wrong/unexplained**. See

  which owns discovery cards.
- **Skill activation is not shown at all.** No node/badge when a skill fires.

### Resource management and performance

- **App-wide FPS degrades over time.** Notably the _visualizer keeps running at full speed_
  while the rest of the app degrades — which points away from GPU/compositor and toward the
  JS thread, a leak, or daemon-message backpressure. Best first move is measurement, not a
  guess: a resource panel (see next item) that makes the degradation visible as it happens.
- **No resource reporting at all.** Wanted: memory/handle accounting across large
  workspaces, chats, tabs, visualizers, diffs — how much we are managing, and protection
  against overwhelming the system. This is a project in its own right, and it is the
  instrument that would diagnose the FPS item above. Related existing work:
  [docs/activity-stats.md](../../docs/activity-stats.md),
  [docs/terminal-performance.md](../../docs/terminal-performance.md).
- **Possible double-counting of background tasks + sub-agents.** Report: "we may be seeing
  double background tasks + sub-agents together." Both tracks render off the session store;
  check whether a provider emits one unit of work into both
  `backgroundShellTasks` and the subagents track.
