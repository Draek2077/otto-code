# Paseo v0.6.1 integration review

## Scope and verdict

Measured on 2026-09-05 at Otto HEAD `7457ca46ec3f4fe0ae329d9f1bcd945954423525`. The user requested the 0.9.0–0.9.2 integration review, but both local and remote Otto tags expose only v0.9.0, and this checkout's package version and changelog still say 0.9.0. This finding covers the actual v0.6.1 merge and all follow-up changes through that HEAD; it does not certify an unidentified 0.9.2 release.

The integration made useful architectural progress and repaired important lifecycle defects. It is not yet a fully verified release, and the measured post-merge work did not reduce subsequent merge conflict cost. Correct Git ancestry and pane-host convergence are real improvements; continued edits in shared composition files and two unmounted integrations remain costs.

## Confirmed integration defects

1. **Plugin Command Center actions never register.** `packages/app/src/plugins/command-center/registration.tsx` exports `PluginCommandCenterActions`, the sole runtime caller of `buildPluginCommandCenterContributions`. No app source imports or mounts it. `packages/app/src/app/_layout.tsx:720` mounts the root/workspace Command Center contributors but omits the plugin contributor. A configured plugin's global/workspace/agent commands therefore never enter Command Center. This contradicts `docs/plugins.md` and the plugin reference. The related remote-main browser run independently fails `plugin-workspace-panels.spec.ts:150` because the “Plugin global action” button is absent. The missing mount is also present at the reviewed local HEAD.

2. **Existing desktop skill selections are not migrated.** The pre-merge desktop stored custom selections in Electron userData's `skill-selection.json` (`integrations/skills/selection-store.ts` at `b6735559a`). The merge moves selection ownership to daemon config. `packages/app/src/agent-skills/legacy-migration.tsx` contains the intended reader/importer and `LegacyAgentSkillsMigration` component, and desktop IPC handlers remain registered, but no runtime source imports or mounts the component. The daemon selection store defaults an unset selection to `{ mode: "all" }`; bootstrap invokes automatic skill maintenance. Existing custom selections are consequently ignored, and a partially installed bundle can be expanded to all bundled skills during maintenance. The on-disk old preference is not deleted, but is unused. This conclusion is established by the before/after persistence and call-site trace, not a launched upgrade simulation. Repair must account for startup maintenance ordering, not merely prove the migration helper works in isolation.

## Measured divergence

Method: enumerate TypeScript/JavaScript modules, including tests and declarations, beneath `packages/` in Git trees. Apply the ordered substitutions in `scripts/rebrand-upstream.pl` to paths and contents and normalize CRLF to LF. Compare full normalized content at matching paths; do not equate a remaining difference with a semantic conflict. Other renames, formatting, binary assets, configuration, and documentation are outside this count.

Of 686 same-path modules changed by upstream from v0.4.0 to v0.6.1, 460 were already Otto-modified before the merge and 472 differ from v0.6.1 at the reviewed HEAD.

## Controlled future-merge rehearsal

Use the same newer upstream snapshot `78b285059f6ebd0b257c98bd191df4626721270a` (fetched upstream/main) against all three Otto states. This is an experiment, not a proposed release target.

Raw `git merge-tree --write-tree --name-only <otto-ref> <upstream-sha>` reports 325 conflicted paths against the initial merge, 332 against v0.9.0, and 337 against the reviewed HEAD. It creates Git objects but does not alter the index or working tree.

To remove branding as a confounder, separately three-way merge normalized same-path package source/test files with `git merge-file -p`, using v0.6.1 content as the common ancestor:

| Otto state | Conflicted files | Conflict hunks |
| --- | ---: | ---: |
| Initial merge | 181 | 797 |
| v0.9.0 | 187 | 821 |
| Reviewed HEAD | 191 | 828 |

This second measurement excludes additions, deletions, renames, non-package code, and non-source files. Hunk count is a mechanical proxy, not developer hours or correctness. It nevertheless supplies no evidence that the repairs made the *same* upcoming changes cheaper to merge. Ten files newly conflict, none stop conflicting, and workspace-screen conflicts rise from 12 to 14 hunks in this sample.

## Architecture assessment

- The merge is a real two-parent commit `4b279544f967f58b39df1aaf30bd1e722e8fceb9`, with actual Paseo v0.6.1 `20d7efc46a316f5a274b9943a5c43b0322269825` as second parent. The About base name/version remains Paseo 0.6.1.
- `WorkspacePanelHost`, the pane registry, Explorer dock, and placement-bearing tab operations are adopted; Otto extends a common host rather than retaining only the old shell. `docs/explorer-sidebar.md` describes the additions explicitly. This is sound direction even though composition files remain modified.
- Hub's daemon/CLI value imports still terminate at the documented disabled boundary in source.
- ProviderSubagentStore is identical after branding normalization, but full subagent convergence is not complete. AgentManager retains separate provider and observed maps; the Claude adapter still owns substantial observed-row ingestion; the client reconciles the two through shadow suppression. Provider-only rows expose fewer controls and accounting fields. This is existing architecture debt, not a newly proven fan-out regression.
- Large shared files remain the expensive seams: AgentManager is 8,459 lines vs upstream's 4,953; Session 12,260 vs 7,524; DaemonClient 10,642 vs 6,244; workspace-screen 5,836 vs 4,359. File size alone is not a defect, but changes here repeatedly overlap upstream.
- An approximate before/after import scan found three newly unused Otto modules. The desktop editor module has a live adopted replacement; the tab-overflow and large-file-notice cases are not reported as user-visible defects without further proof. The plugin registration and migration findings came from scanning *new upstream integrations* as well, which the Otto-only orphan guard does not cover. Import count alone also cannot prove a React component is mounted.

## Verification and limits

At reviewed HEAD: `npm run lint` passes with zero warnings/errors; `npm run typecheck` passes; `messages.wire-compat.test.ts` passes 9 tests; five selected AgentManager steer/replacement/submission-identity tests pass (170 other tests in that file intentionally deselected). No full local suite or interactive cross-platform upgrade simulation was run.

There is no GitHub Actions run for reviewed HEAD. Local and remote main diverge by 2 local-only and 6 remote-only commits. Related remote-main CI run [33924801496](https://github.com/Draek2077/otto-code/actions/runs/33924801496), at `3759502db`, is red: server tests on both platforms, all eight browser shards, desktop overlay, and Linux Electron browser bridge. One browser shard and one CLI shard stopped on agent-CLI installation ETARGET; other browser shards actually executed tests and failed. Passing jobs include app units, SDK, relay, lint, typecheck, Android-native tests, and Windows desktop units.

Do not interpret every red job as a product defect: the Linux artifact resolver assertion uses a Windows drive spelling with an unnormalized expected path; the Windows workflow failure is ENOTEMPTY during cleanup, alongside four worker-exit errors. The Linux worktree assertion and remaining browser failures require triage. The Electron bridge timed out waiting for the seeded sidebar workspace before exercising its browser assertions.

## Recommended follow-up

First restore the two missing integrations and validate their complete app/upgrade paths. Then establish an exact candidate commit with a passing CI matrix, separating genuine regressions from obsolete assertions and infrastructure failures. Extend merge acceptance beyond the Otto-only orphan snapshot to new upstream registrations, context providers, IPC/RPC wiring, and a small behavior matrix for compact/wide, native/web/Electron, and provider coverage. Preserve upstream mechanisms and extract Otto policy from recurring shared hotspots only when a measured change reduces the patch. Repeat a normalized rehearsal against the same pinned upstream target to evaluate that reduction.

These are findings and recommendations, not an approved refactor plan. Related policy: [[upstream-mergeability-through-otto-owned-seams]]; remaining subagent work: [[upstream-subagent-convergence]].
