# October FPS regression: a transient GPU crash latched software compositing, and parked browser tabs are never throttled

<!-- compiled_truth -->

The FPS regression reported on 2026-10-08/09 is primarily environmental to the app, not a JS regression. A single GPU-process crash on 2026-10-08 17:57 (exitCode 34, WebGL context lost) wrote the disable-hardware-acceleration marker, and every capture since then runs with software compositing. Under software compositing the worst frames run 100 to 230 ms with zero script and under 1 ms of style and layout, so the cost is CPU raster and compositing. Browser tabs amplify this: parked resident webviews are deliberately kept visibility: visible at a 1x1 paintable geometry, so Chromium never applies hidden-page throttling to them. Separately, the Codex app-server transport dropped any JSON-RPC response containing U+2028/U+2029, because node:readline treats those as line breaks; the dropped responses were retried and logged in full, at about 30 MB of daemon log per hour.

Verified: the software latch and its timestamp; the frame shape (no script, no layout); the readline split, reproduced in a unit test and fixed by newline-only framing. Hypothesis, not yet measured: how much of the per-frame cost is guest-webview compositing versus the app's own animated surfaces (for example a running agent tab writing style twice per frame). Also unexplained: a one-time Windows Tcpip 4231 ephemeral-port exhaustion event at 17:57:34, eleven seconds after the GPU crash.
